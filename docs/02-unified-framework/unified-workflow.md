# 统一工作流框架 · 10 阶段端到端 AI 软件开发

> 融合 Spec Kit、BMAD、AI-DLC、gstack、Agentic OS 五大框架，并叠加自有闭环保障体系，沉淀出的"最全"主流程。
> 每一阶段都给出：**输入 → 活动 → 产出物 → 放行门禁 → 对应框架做法 → 主责角色**。

## 总体流程图

```
                          ┌──────────────────────────────────────────┐
                          │  G0 治理基线（每项目一次）                  │
                          │  constitution + 角色 + 门禁 + 工具链        │
                          └────────────────────┬─────────────────────┘
                                               ▼
   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ G1 想法   │→ │ G2 澄清   │→ │ G3 规格   │→ │ G4 计划   │→ │ G5 任务   │
   │ 评估     │   │ 启动     │   │ 需求     │   │ 架构     │   │ 拆解     │
   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └────┬─────┘
                                                                     ▼
   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ G10 反馈  │← │ G9 发布   │← │ G8 测试   │← │ G7 代码   │← │ G6 构建   │
   │ 迭代     │   │ 交付     │   │ 验证     │   │ 审查     │   │ 实现     │
   └────┬─────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
        │
        └──────────────────→ 回到 G3（需求落地反馈闭环，驱动下一轮规格修订）
```

**规模自适应**（借鉴 BMAD / Spec Kit 的三条入口）：并非每个变更都要走完 10 阶段：

| 变更类型 | 建议起点 | 路径 |
|---|---|---|
| 小改动（typo、小 bug） | G6 | G6 → G7 → G8 → G9（轻量门禁，约 5k tokens） |
| 功能开发 | G2/G3 | G2 → G3 → … → G9 → G10 |
| 想法/新项目评估 | G1 | G1 →（go）→ G3 或 G0 → … |
| 企业级/受监管系统 | G0 | 全 10 阶段 + 全部审计门禁 |

## G0 · 治理基线（Governance Baseline）

> 每个项目建立一次，是所有后续阶段的"宪法"。借鉴 Spec Kit `/constitution` + Agentic OS 治理层。

| 项目 | 内容 |
|---|---|
| **输入** | 项目目标、团队规模、合规要求、技术偏好 |
| **活动** | 定义质量原则；确定角色分工；配置质量门禁；选择工具链与宿主；建立审计与记忆机制 |
| **产出物** | 项目宪法（constitution）、角色矩阵、门禁配置、工具链清单、单一事实源目录 |
| **放行门禁** | Gate 0：原则明确、角色到位、门禁可机器校验 |
| **对应框架** | Spec Kit `/constitution`；Agentic OS 治理文件（CLAUDE.md / AGENTS.md / GEMINI.md）+ git hook |
| **主责角色** | 项目经理 / 技术负责人 / 治理官 |

**项目宪法模板要点**：代码质量标准、测试覆盖率门槛（如 ≥80%）、可维护性要求、安全基线、命名规范、变更审批规则。

## G1 · 想法评估（Idea Assessment）

> 用证据决定一个想法是否值得投入。借鉴 Spec Kit `/assess-*`。

| 项目 | 内容 |
|---|---|
| **输入** | 想法描述、现有代码库（可选） |
| **活动** | 收集证据 → 定义价值 → 评估形态/可行性 → 决策 |
| **产出物** | 评估报告、`decision.md`（结论：`go` / `needs-clarification` / `kill`） |
| **放行门禁** | Gate 1：结论为 `go` 且证据充分，才进入 G2/G3 |
| **对应框架** | Spec Kit `/assess-intake → research → define → shape → decide` |
| **主责角色** | 产品经理 / 创始人顾问 |

> 关键：**带着充分理由停下（kill）也是一种有效产出**，不必每个想法都进入开发。

---

## G2 · 澄清与启动（Clarify & Inception）

> 把模糊想法变清晰，建立已验证的上下文。借鉴 BMAD Clarify + AI-DLC Inception。

| 项目 | 内容 |
|---|---|
| **输入** | 已批准的想法（go）、现有代码库上下文 |
| **活动** | 澄清模糊点；建立上下文；识别约束与风险；确定规划路径 |
| **产出物** | 澄清记录、上下文文档、风险清单、规划路径决策 |
| **放行门禁** | Gate 2：关键 ambiguities 已消解，上下文可支撑规格编写 |
| **对应框架** | BMAD Clarify；AI-DLC Inception 阶段 |
| **主责角色** | 产品经理 / 业务分析师 / 架构师 |

---

## G3 · 规格与需求（Specify / PRD）

> 把"做什么、为什么"写清楚，先不碰技术实现。借鉴 Spec Kit `/specify` + BMAD PRD。

| 项目 | 内容 |
|---|---|
| **输入** | 澄清后的需求、上下文文档 |
| **活动** | 编写规格 / PRD；用户故事 + 验收标准（Gherkin）；设计系统约束 |
| **产出物** | 规格说明书 / PRD、用户故事、验收标准、ID 溯源映射 |
| **放行门禁** | Gate 3：规格完整、可测试、ID 全链路可追溯（见闭环体系） |
| **对应框架** | Spec Kit `/specify`；BMAD PRD / Gherkin 验收 |
| **主责角色** | 产品经理 / 需求分析师 |

**ID 溯源要求**（自有体系）：每个需求分配唯一 ID，向下贯穿任务、代码、测试、发布，用箭头展示流向，实现全链路绑定。

---

## G4 · 计划与架构（Plan & Architecture）

> 把规格转成技术方案与架构决策。借鉴 Spec Kit `/plan` + BMAD Architect/ADR + AI-DLC 专家 Agent。

| 项目 | 内容 |
|---|---|
| **输入** | 规格 / PRD、验收标准 |
| **活动** | 技术选型；架构设计；API/数据模型设计；写 ADR（架构决策记录） |
| **产出物** | 技术选型报告、架构设计文档、ADR、架构图、数据模型 |
| **放行门禁** | Gate 4：架构对齐规格、决策有据（ADR）、安全与可维护性评审通过 |
| **对应框架** | Spec Kit `/plan`；BMAD Architect + ADR；AI-DLC 11 领域专家 |
| **主责角色** | 架构师 / 技术负责人 |

---

## G5 · 任务拆解（Task Breakdown）

> 把规格与计划拆成可执行、可分配的任务。借鉴 Spec Kit `/tasks` + BMAD Epics/Stories。

| 项目 | 内容 |
|---|---|
| **输入** | 规格、架构、ADR |
| **活动** | 拆 Epic → Story → Task；标注依赖与优先级；绑定需求 ID |
| **产出物** | 任务清单、依赖图、优先级队列、需求→任务 ID 映射 |
| **放行门禁** | Gate 5：任务覆盖全部验收标准，依赖清晰，ID 可追溯 |
| **对应框架** | Spec Kit `/tasks`；BMAD Epics/Stories |
| **主责角色** | 项目经理 / 技术负责人 |

---

## G6 · 构建实现（Build / Implement）

> AI Agent 按任务编码，人做方向把控。借鉴 Spec Kit `/implement` + gstack 角色工具 + AI-DLC 构建阶段。

| 项目 | 内容 |
|---|---|
| **输入** | 任务清单、架构、代码库 |
| **活动** | 逐任务实现；TDD（功能开发）；按阶段自动挂载技能清单；保持上下文 |
| **产出物** | 可运行代码、数据模型、API 实现、单元测试 |
| **放行门禁** | Gate 6：任务完成、代码可编译、单元测试通过、无凭证泄露 |
| **对应框架** | Spec Kit `/implement`；gstack 23 角色工具；AI-DLC 构建阶段；Agentic OS 凭证扫描 |
| **主责角色** | 开发工程师 / AI 编码 Agent |

> 纪律（Agentic OS）：先规划后编辑、不做未被要求的重构、凭证扫描必须在门禁处拦截。

---

## G7 · 代码审查（Review）

> 多角色审查，确保实现符合规格与质量标准。借鉴 BMAD code-review + AI-DLC 审查者 + gstack 互审。

| 项目 | 内容 |
|---|---|
| **输入** | 代码变更、规格、架构 |
| **活动** | 代码审查；安全审查（登录/鉴权代码）；规格一致性检查；审查证据留痕 |
| **产出物** | 审查报告、问题清单、溯源审查证据 |
| **放行门禁** | Gate 7：无阻塞问题，审查有据可查，来源绑定 |
| **对应框架** | BMAD `code-review` / `bug-analyzer`；AI-DLC 2 审查 Agent；gstack 角色互审 |
| **主责角色** | 审查者 / 安全工程师 / 技术负责人 |

---

## G8 · 测试与验证（Test & Verify）

> 用真实测试证明质量，拒绝"测试通过但没测试"。借鉴 Spec Kit `/converge` + Agentic OS 测试门禁 + BMAD 测试架构。

| 项目 | 内容 |
|---|---|
| **输入** | 代码、验收标准 |
| **活动** | 单元/集成/E2E 测试；覆盖率检查；收敛验证（实现 vs 规格）；记录测试证据 |
| **产出物** | 测试报告、覆盖率报告（≥80%）、收敛报告（`Converged`）、测试运行指纹 |
| **放行门禁** | Gate 8：覆盖率达标、测试真实运行、`converge` 报告 Converged、代码在测试后未变更 |
| **对应框架** | Spec Kit `/converge`；Agentic OS `record_test_run.py`；BMAD Test Architect |
| **主责角色** | 测试工程师 / QA |

> 机器强制（Agentic OS）：测试退出码 + 代码指纹被记录，若测试失败或测试后代码被改动，`/ship` 校验失败。

---

## G9 · 发布交付（Ship / Deploy）

> 生成部署与运维产物，受审批门与变更流程约束。借鉴 AI-DLC Operations + Agentic OS `/ship` + 自有变更流程。

| 项目 | 内容 |
|---|---|
| **输入** | 通过 Gate 8 的代码、变更请求 |
| **活动** | CI/CD 流水线；部署；生成运维手册/监控配置；变更审批；告警规则配置 |
| **产出物** | 部署包、CI/CD 配置、运维手册、监控/告警配置、变更记录 |
| **放行门禁** | Gate 9：变更经 AI 评估 + 审批、测试证据有效、告警与回滚就绪 |
| **对应框架** | AI-DLC Operations；Agentic OS `/ship` + `validate.sh`；自有变更流程（在线表单 + AI 评估） |
| **主责角色** | 运维工程师 / 发布经理 |

---

## G10 · 反馈迭代（Learn & Iterate）

> 需求上线后收集反馈，驱动下一轮规格修订，形成闭环。借鉴 BMAD Learn + 自有闭环体系。

| 项目 | 内容 |
|---|---|
| **输入** | 上线反馈、监控指标、用户行为 |
| **活动** | 智能反馈路由（三类自动分类）；健康度仪表盘分析；经验沉淀到知识库；版本迭代 |
| **产出物** | 反馈分类报告、健康度报告、知识库更新、下一轮需求/规格修订 |
| **放行门禁** | Gate 10：反馈已分类并进入待办，知识库已更新，体验问题已追踪 |
| **对应框架** | BMAD Learn & Adjust；自有智能反馈路由 + 动态知识库 |
| **主责角色** | 产品经理 / 运营 / 项目经理 |

**闭环关键**：G10 不是终点，而是通过"需求落地反馈迭代"回到 G3，形成真正的闭环——这正是本项目"全流程闭环"的核心。

## 落地建议

1. **从 G0 开始**，先把宪法、角色、门禁、工具链固化下来——这是所有后续阶段的地基。
2. **按变更规模裁剪**：不要让 typo 修复走 10 阶段，也不要让企业系统跳过审计。
3. **门禁必须机器强制**：借鉴 Agentic OS，把能自动化的门禁（凭证扫描、覆盖率、阶段证据）接进 git hook 与 CI。
4. **闭环一定要回到 G3**：G10 的反馈若不能驱动规格修订，闭环就是断的。
